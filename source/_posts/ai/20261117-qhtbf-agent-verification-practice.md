> **Too Long; Didn't Read**：当 Claude Code 团队约 90% 的代码由 Claude 编写和评审时，瓶颈从"写代码"转移到"验证代码"。他们的答案是**把验证当作一个独立系统来工程化**，而不是 agent 的一次自查动作。剥掉具体做法，核心只有四条铁律：**判卷规则不可被考生修改、完成必须有证据、漏检要变成规则、规则要定期修剪**。做到这四条，人的角色才能从"读每个 diff 的审查者"退到"定义 done 的人"，Agent 并行交付的规模上限随之打开。

## 写在前面：问题变了

> 原文：[How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)（Addy Osmani，2026-11-16）

在 Claude Code 团队，绝大多数代码（约 90%）由 Claude 编写和评审。在这个规模下，**验证回路（verification loop）不是质量锦上添花，而是并行扩展的前提**：

- 没有验证回路 → 每个变更都要人亲自看 → 你只能同时跑一两个 agent；
- 有了验证回路 → agent 能自己用证据证明"done" → 你可以并行跑几十上百个。

原文给出的一个关键实验数据：在结构化文件生成的内部测试中，用一个**独立的 grader 按 rubric 检查** Claude 的工作，比标准 prompting loop 的任务成功率最高提升 **10 个百分点**，而且最难的任务收益最大。

这里藏着一个经济学层面的转折：**测试、基准、E2E 运行以前是"贵"的（要人写、要人维护），现在让 agent 生成一次之后，它们以软件形态反复运行，边际成本趋近于零**。验证从人力成本变成了固定资产——这是整篇文章成立的前提。

本文分两部分：先拆解原文的核心内容，再讨论一个通用 coding agent（不限 Claude Code）该如何把这套东西落地。

## 一、三个值得记住的事实

| 事实 | 含义 |
| --- | --- |
| 独立 grader 按 rubric 检查 agent 的工作，任务成功率最高 +10 分，最难的任务收益最大 | **判卷人与做题人分离**，是最便宜的提分手段 |
| 测试 / 基准 / E2E 以前"贵"、现在"便宜" | 验证器生成一次后以软件形态运行——**从人力成本变成固定资产** |
| 可靠性清单 39 项，每次 diff 只命中 3-10 项 | 规则要挂在"可从 diff 判定的触发器"上，而不是全量人肉背诵 |

还有一个前置警告，比"该选哪种测试"更重要：

- **flaky 测试会训练 agent"重跑而不是修复"**——它会学会碰运气；
- **慢测试会减少验证频次**，让问题定位变难；
- 重的测试应该部署在**提交边界**（commit / PR 之前）。

## 二、三种值得投资的测试

原文明确说：如果只投一种，选 E2E。三种类型对比：

| 类型 | 本质 | 为什么对 agent 特别有效 |
| --- | --- | --- |
| **E2E 测试** | 真实用户流整条跑通（加购 → 结算 → 确认页） | **难以欺骗**——要么整个功能工作要么不工作；有明确的 done 判据；能给出截图级别的"哪里坏了"，而不是 `Error: Timeout after 30 seconds` |
| **属性测试** | 声明"不可能失败"的约束，用测试库生成上千输入去证伪 | 边界输入**不是由与被测代码同源 bias 的 mind 生成的**，专治 agent 的系统性盲区；spec 漂移时仍然可用 |
| **差分测试** | 旧系统当 oracle，新旧系统同输入比对输出 | 迁移 / 重写场景的守门员；随机输入或生产流量采样；需归一化无关差异 + 维护"允许变更"白名单 |

几个值得展开的点：

**E2E 要给 agent "手和眼"。** 用 skill 启动真实系统并用 CDP、模拟器、API harness 去驱动和检查它。feature map（从用户视角列出功能、路径、快捷键、选择器、预期结果）天然就是 agent 的评分 rubric。

**属性测试治的是"同一个脑子"。** agent 写代码和 agent 写测试用的是同一个 bias，所以普通单元测试对它的盲区无能为力。属性测试库（JS/TS 的 fast-check、Python 的 Hypothesis、Rust 的 proptest）生成的输入没有这个 bias。四类常见属性：

- **Round-trip**：编码再解码，得到原值（解析、序列化通用）；
- **不变量**：永远为真的约束，如"账户余额不能为负"；
- **幂等**：迁移、归一化、重试执行两次等于执行一次；
- **等价**：优化后的代码与朴素但正确的版本产出相同结果。

**差分测试的三个细节**：输入用随机生成或生产流量采样；归一化空白符等无关差异；维护一份 approved changes 白名单，列出新系统"就应该不同"的地方。

## 三、Claude Code 团队的九条实践

原文的实践部分可以压缩成四组，每组都在解决一个明确的问题：

### 第一组：验证即运行

1. **Verification means running the change**。跑真实系统比跑测试更重要——"你不会不试模拟器就发 iOS 版本，对 Claude 也一样"。具体做法是写一个叫 `verify` 的 skill 放在 `.claude/skills/`，告诉 agent 怎么启动 app、怎么冒烟测试，并且 Claude 知道提交前要先跑它。verify harness 本身要被反复压测到 rock solid——它是所有下游验证的地基。

### 第二组：人机分工

2. **Failing tests require human attention**。Claude 自己修，同一失败修 3 轮还不好 → 停下来叫人。没人能读每个 diff，**失败是决定"什么需要人看"的主要信号**。
3. **Code owners write their own checks**。检查由代码 owner 自己写、反复打磨，直到它标记的问题正是 owner 会标记的问题；且检查拉人进来时必须**说清楚为什么**，而不是让人自己从 diff 里猜。
4. **Reliability checks trigger on the diff**。39 项可靠性清单，每项都有：可从 diff 读出的触发器、检查内容、背后的事故 / PR。agent 读 diff 只检查命中触发器的 3-10 项——没人需要背历史事故，历史事故自己会跳出来。

### 第三组：反作弊（最容易被忽略的一组）

5. **Changes can't modify their own checks**。如果变更能修改审判自己的规则，规则就废了。Code Review 从 **base / 默认分支**读 REVIEW.md，绝不从 PR 的变更里读。评审绑定 commit：评审期间推了新提交，评审结果作废（过时的通过毫无意义）。便宜的门先跑：先本地测试 / 构建 / lint，再开 PR，别把共享的评审和 CI 时间浪费在自己能拦住的 bug 上。
6. **One reviewer, multiple rounds**。不靠堆 reviewer 数量提升质量——"在主 reviewer 之上加第二个更贵的 reviewer，往往不如调优主 reviewer"。用一个 REVIEW.md 定义这个 reviewer 该看什么；且**每一轮评审建立在前几轮的发现和历史失败之上**，而不是从零复查，更便宜也捞得更多。

### 第四组：验证体系自治理

7. **Start a new gate in observe mode**。每个 commit 盖验证戳，戳里显式包含 `none`——"没验证"变成可查询的状态而不是不可见。新门有 off / observe / enforce 三档：observe 只记录"本应拦截什么"，用来排查误伤；enforce 真拦截，但 commit message 可以带解释，同一会话被拦两次后放行——**门要硬，但要有逃生门，防止 agent 卡死**。
8. **Test your checks on what actually matters**。定期 review the reviewers：统计 revert 率、maintainer 拒绝率；用历史事故和 revert 构造正式评测——每个例子重建当时的仓库状态、配一句话答案（answer key），**只有正确指出那个 bug 才得分**，用稳定的已合并变更做对照组防过度拦截；recall 分阶段统计（原始发现 → 验证后 → 终审），看系统有没有把已经找到的 bug 弄丢；调参停在"再调就是过拟合评测集"的边缘。发现的严重度分级：Important / Nit / Pre-existing——Pre-existing 意味着不该让当前作者背锅。
9. **Turn misses into rules**。漏检不白漏：从人审评论和 revert 中提取模式（至少出现在 2 个 PR、可从 diff 识别才算候选），派 3 个 agent 尝试证伪，再人审合入；对已知事故关联的 PR 回放 3 个 bug finder，至少 2 个找到才算"可检测 bug"，小 diff 上漏掉就是要写进 REVIEW.md 的缺口。flaky 测试同样铁腕：**不许 skip、不许加 sleep、不许重试到绿**，找不到根因就删掉测试并写明原因。规则本身也要定期修剪——测试、验证步骤和 .md 文件只会越攒越多。

## 四、四条设计原则

剥掉具体做法，这篇博客真正在讲四条原则——它们也是落地时的理论依据：

1. **验证是可复利的资产**。一次生成、永久以软件形态运行。投入顺序应该是"先把验证器做扎实"，而不是"多生成几遍代码"。
2. **判卷人独立性是第一设计约束**。"变更不能修改审判自己的规则"、独立 grader +10 分、属性测试用不同 bias 的输入生成器——全部指向同一个洞见：**agent 自查的瓶颈不是能力，而是它与被测代码共享同一个盲区**。
3. **要证据链，不要自述**。agent 说"测试通过了"不算数；截图、日志、退出码、验证戳才算数。评审必须绑定具体 commit，否则证据随时间失效。
4. **验证体系本身也是软件**。它会有 bug、会腐化、会过拟合，所以它自己也需要灰度上线（observe → enforce）、元评测和定期修剪。

## 五、通用 Agent 如何落地

Claude Code 有 `.claude/skills/verify` 这个仓库内约定。一个通用 coding agent 没有这个约定，需要构造等价物。下面是可以直接照抄的落地蓝图。

### 5.1 一次交付的验证闭环

任何 agent 的单次交付都可以抽象成同一条闭环：

```
生成变更 → 验证流水线（cheap-first） → 证据落盘 → 通过则交付（评审绑定 commit）
                ↓ 失败
          修复循环（同一失败 ≤3 轮） → 仍失败 → 带证据与上下文升级人类
```

流水线内部是分层的，**便宜的门先跑、跑得勤，贵的门放在提交边界**：

| 层 | 内容 | 成本 | 关键点 |
| --- | --- | --- | --- |
| L0 静态门 | build / lint / typecheck / vet | 秒级 | 每轮改完必跑；开 PR 前必须全绿 |
| L1 单元 + 属性测试 | agent 生成属性陈述，人审一次后固化 | 分钟级 | 属性输入由 fast-check / Hypothesis 独立生成，与 agent 的 bias 解耦 |
| L2 E2E 冒烟 | verify 脚本启动真实系统（CDP / 模拟器 / API） | 分钟级 | 难以欺骗；截图即证据；feature map 即评分 rubric |
| L3 差分测试 | 迁移 / 重写时新旧系统对拍 | 重、按需 | 随机输入或生产流量采样 + 归一化 + 白名单 |

### 5.2 六个关键机制

**① verify 声明化。** 通用 agent 需要一个声明式 verify manifest：记录"怎么 build、怎么起、done 长什么样"。可以放在 repo（skill / 脚本），也可以由 agent 首次进入项目时生成、人类确认一次后固化。manifest 本身要被压测到 rock solid——它是全部下游验证的地基。

**② 证据协议。** "完成"的定义不是 agent 说完成，而是**证据齐了**：退出码由 harness（agent 之外的执行环境）收集、截图、测试原始输出。agent 只能引用证据，不能转述证据。给每个 commit 打验证戳，且戳里显式包含 `none`——"未验证"变成可查询、可统计的状态。

**③ 判卷独立性。** 最反直觉也最关键的一条：agent 生成的变更**不能修改审判自己的规则**。工程上意味着——判卷规则从 base 分支或独立配置读取；验证结果由外部 harness 收集而非 agent 自报；属性 / 差分测试的输入用独立生成器。条件允许时，grader 用不同的 session 甚至不同的模型，进一步对消共享盲区（+10 分的实验就是这个思路的实证）。

**④ 升级策略与 flaky 治理。** 同一失败最多修 3 轮，之后带证据升级人类——这是防止 agent 无限空转的止损线。flaky 测试铁腕治理：禁止加 sleep、禁止重试到绿、禁止 skip；找不到根因就删测试并写明理由。否则 flaky 会系统性地把 agent 训练成"重跑碰运气"。

**⑤ 漏检转化为规则。** 每次真实漏检（事故、revert、人审捞到的 bug）都不白漏，经对抗验证后变成可从 diff 触发的规则，让同一个坑只踩一次：

```
真实漏检（事故 · revert）
    → 规则候选（≥2 次出现 · diff 可识别）
    → 对抗验证（3 个 agent 尝试证伪 · 人审合入）
    → 规则生效（REVIEW.md / 可靠性清单，observe → enforce）
    → 新漏检再进入 · 规则定期修剪
```

这个闭环里有三个门槛，缺一个都会退化成"规则垃圾场"：

- **准入门槛**（≥2 个 PR 出现 + diff 可识别）：单次事故不成规则，防止把偶发问题固化成噪音；
- **对抗门槛**（3 个 agent 证伪 + 人审）：规则本身也会过拟合，先让别人推翻它；
- **退出机制**（定期修剪）：清单和 REVIEW.md 只会增长不会收缩，放任不管会拖慢每一次验证。

**⑥ 元验证（review the reviewers）。** 验证器自己也需要被验证：用真实事故 / revert 构造 golden set（带一句话答案 + 干净变更对照组）；分阶段统计 recall（原始发现 → 验证后 → 终审）；发现按 Important / Nit / Pre-existing 分级，避免 nit 噪音淹没 must-fix；调参停在过拟合边缘。

### 5.3 落地优先级

| 阶段 | 做什么 | 标志 |
| --- | --- | --- |
| P0（当天可做） | cheap-first 门（build / vet / test）+ 同一失败 ≤3 轮升级 + 完成必须有证据 | agent 不再"自述完成" |
| P1 | verify manifest / skill + E2E 冒烟 + 验证戳（含 none）+ 门先 observe | "未验证"变成可查询状态 |
| P2 | 属性 / 差分测试 + 漏检 → 规则闭环 + 元评测 | 同一个坑只踩一次 |
| 成熟 | 人从"读每个 diff"变成"定义 done + 抽查证据" | 能并行开几十个 agent 的真正前提 |

## 六、几个反直觉但真实的坑

以下几类坑在实际工程里反复出现，每一个都精确对应上文的一条原则：

| 实际发生的坑 | 对应原则 |
| --- | --- |
| 工具 / agent 回报 `success`、`Exit Code: 0`，但文件实际没改 | **证据协议**：自述不可信，可信的是外部 harness 捕获的落盘结果 |
| 自己写的校验脚本报 FAIL，最后发现是校验器自己的 bug（标题带后缀导致误判、正常引用被当成重复） | **元验证**：验证器是一等公民软件，本身需要 golden set 校准，FAIL 和假绿都要防 |
| 补丁脚本重跑时在"锚点已不存在"上崩溃，看起来像首轮根本没写盘 | **flaky 治理**：重跑必须可判定、可收敛（如 already-applied 检测），禁止"重试到绿" |
| agent 被硬门拦住无限重试，任务卡死 | **逃生门**：拦两次后放行 + commit message 带解释 |

共同教训：**验证层不是 agent 的附属品，而是一个与生成方利益隔离的独立系统**。它越独立，越可信。

## 写在最后

原文结尾有一句值得原样记住的话（意译）：

> 把你的验证层当成任何一个正经系统来对待：让它远离它所审判的变更、用真正重要的 bug 给它打分、漏检时把教训写下来、定期修剪这些教训让它们始终值得运行。

做到这些，工作性质就变了：**从读每一个 diff，变成定义"done"长什么样、然后审查证据**。这才是"几十上百个 agent 并行"的真正前提——不是模型更强，而是验证体系让"信任"可以批量发放。
