> **Too Long; Didn't Read**：判断一个新流程要不要做成 Skill 或 MCP，别问"AI 会不会"，要问"它缺哪类东西"——信息 / 权限 / 方法 / 确定性 / 责任 / 连通性 / 强制性。**把 MCP 想成 Agent 用的自定义 SDK**（凭证与连接藏在服务端，Agent 只拿到带 schema 的工具），技能则是这份 SDK 的使用说明书。命中 MCP 六条硬门槛任一条 → 必须 MCP；命中技能六条硬门槛任一条 → 必须技能；都不中按频率走本地库或对话内联；凭证永远只在服务端、不进对话不进技能。

## 写在前面：团队里反复吵的三个问题

只要团队开始认真用 Agent 干活，几乎一定会冒出同一组争论：

- "在对话里发个密码不就能连环境？为什么要单独做成技能？"
- "截图 AI 自己就能看，为什么还要 OCR 技能？"
- "这个流程到底要不要单独弄一个技能？还是该做成 MCP？"

没有统一标准时，会出现三种"病症"，每一种都有实打实的代价：

| 病症 | 表现 | 代价 |
| --- | --- | --- |
| **技能泛滥** | 把通用能力各自包一个技能，同类实现重复维护 | 重复实现、上下文膨胀、脚本漂移 |
| **技能缺失** | 关键方法只存在于个人经验或某次对话里 | 换个人 / 换个 Agent 就做错、漏做，甚至越过安全边界 |
| **能力错位** | 该由 MCP 持有的凭证、连接、硬护栏，被塞进技能或脚本里 | 凭证暴露给 Agent、护栏只靠"建议"、沙箱连不上目标系统 |

本文想给出一条**可执行、可复用、抗老化**的判定标准，同时把边界讲清楚。它回答三件事：

1. **判定**：一个新场景 / 新流程，要不要单独做成 Skill？要不要做成 MCP？
2. **边界**：AI 能直接做什么，什么必须落实到 Skill，什么必须落实到 MCP？为什么？
3. **分工**：Skill 与 MCP 如何配合，各自的硬 / 软约束放在哪？

## 一、核心结论：先定"轴"，再判断

最容易被忽视的一点：判定标准该以**什么**为轴？

很多人下意识拿"AI 能力"做轴——"AI 现在不会做 X，所以要做技能；等模型变强了就删掉"。但模型半年一变，这种文档半年就过时，今天写"AI 不能做 Y"，下个版本就成笑话。

本文的轴是**缺口类型**：信息、权限、方法、确定性、责任、连通性、强制性。模型会变强，**缺口不会消失**——用缺口做轴，文档才不会半年就过期。

一句话结论（这是全文的脊梁）：

> **技能承载"方法与契约"（软约束），MCP 承载"能力与强制"（硬约束），二者都不承载"凭证本身"。**

更口语一点：**技能是"怎么做才对"（脑），MCP 是"能连到哪、能做什么、谁在强制"（手）。**

再换成开发者的语言：**MCP 就是 Agent 用的自定义 SDK**——把连接、凭证、权限、审计封成 Agent 能调用的能力；技能则是这份 SDK 的"使用说明书"（下一节展开）。

判定一个流程要不要做成技能或 MCP，不问"AI 会不会"，而问它缺的是下面哪类东西：

| 缺口 | 具体表现 | 应该补在哪 |
| --- | --- | --- |
| **信息** | 私有、版本化的领域事实（组件、路径、端口、调用链、案例） | 知识库 |
| **权限** | 凭证、内网、浏览器 / SSO 认证、外部平台 | 密钥管理 + **MCP**（由服务端持有并注入） |
| **方法** | 隐形操作步骤、流程状态机、不可逆操作的护栏 | **技能** |
| **确定性** | 解析、对账、计算、分页去重、流式解析等复杂逻辑 | 技能内脚本 / 本地库 |
| **责任** | 不可逆或对外可见的写操作，需要人担责 | **技能的确认门 + MCP 的审批 / 权限 + 人工** |
| **连通性** | 目标系统在内网、需要 SSO / OAuth、需要常驻或有状态连接，Agent 沙箱本身到不了 | **MCP** |
| **强制性** | 权限分级、审批、审计、限流必须在协议层强制，而不是靠"建议 Agent 遵守" | **MCP** |

还有两类"软缺口"值得单列：

- **一致性**：多人、多 Agent、多会话需要同一行为（规范、口径、模板）。
- **可发现性**：不写下来，Agent 就不知道这项能力存在。

> 一句话记法：**纯 AI 不是"不会想"，而是"不知道私有事实、进不去内网、拿不到凭证、不该独自做不可逆操作、每次重写不确定、也没人在底层强制它守规矩"。**

## 二、MCP vs SDK：把 MCP 想成 Agent 用的自定义 SDK

"手 / 脑"的比喻如果还偏抽象，换成开发者最熟的东西会立刻具体：

> **MCP 就是 Agent 使用的自定义 SDK。** 传统 SDK 由平台方提供给开发者，开发者在代码里 `import`；MCP 由服务方部署，Agent 在运行时连接、按工具名调用。除此之外，二者封装的东西几乎是同一类。

一套 SDK 其实卖两样东西：**能调用的能力**（函数、类型、凭证处理、连接管理），以及**该怎么用**（文档、示例、注意事项）。传统开发里这两样是分开的——前者在代码包里，后者在文档里给人读。到了 Agent 场景：

- **能力面 → MCP**：连接、凭证、权限、审计、结构化输入输出，全部封进服务端，暴露成一组带 schema 的 tool；
- **用法面 → 技能**：调用顺序、状态机、写操作前必须确认，写成技能给 Agent 读。

一句话：**MCP 是这份"Agent SDK"的能力包，技能是它的使用说明书；合起来才是 Agent 能正确用好的一套 SDK。**

| 传统 SDK 里的东西 | MCP 里的对应物 | 为什么需要它 |
| --- | --- | --- |
| SDK 方法 / 函数签名 | MCP tool + tool schema | 机器级契约，Agent 才知道参数类型与边界 |
| 初始化时注入的凭证（env / 凭证文件） | 服务端持有，Agent 只传业务参数 | 凭证不进对话、不进上下文 |
| 连接池 / token 刷新 / 长连接 | 有状态常驻连接 | Agent 沙箱到不了内网，会话要维持 |
| 权限校验 / 限流 / 审计中间件 | 写 tool 单独拆出 + 审批 / 权限 / 审计 | 硬拦截，不靠"建议 Agent 遵守" |
| README / 示例 / 注意事项 | 技能（流程、状态机、确认门） | 换个 Agent 会做错、漏做、越界 |
| 多语言 binding | 标准协议，多客户端复用 | 一套服务端，多种 Agent / 客户端接入 |

### 为什么不能直接用原始 API 或普通 SDK

- **直接把原始 HTTP API 暴露给 Agent**：凭证会进上下文、沙箱连不通内网、护栏只能靠"请遵守"，而且每个 Agent 都要各写一遍适配——这正是下面 MCP 六门槛要解决的。
- **把普通 SDK 丢给 Agent 用**：SDK 假定调用方是确定性程序，人写代码时显式 `import`、版本固定；Agent 是运行时动态发现工具，可能漏读、误读甚至被注入。所以硬护栏必须落在服务端——这就是"双层护栏"的根因。

### 这个比喻在哪里不成立

诚实地说，类比有三处边界：

- SDK 是被显式引入、版本固定的；MCP 工具是运行时发现的，schema 一变就可能破坏 Agent 的调用——需要独立的契约回归与版本兼容（见文末"没展开"部分）。
- 传统 SDK 的凭证常在调用方环境里；MCP 把凭证收到服务端——这是安全模型的本质差别，也是它不能简单等同的原因。
- SDK 往往一语言一个包；MCP 是跨语言的协议层，天然面向多客户端。

记住这一句就够：**MCP = Agent 用的 SDK 的能力面（硬），技能 = 它的使用说明书（软），凭证谁都不给、只留在服务端。**

## 三、判定流程：先看 MCP，再看 Skill，最后看频率

### 第一步：先判断是否需要 MCP（能力与强制）

流程是否要碰外部系统、凭证或状态？

- **否** → 跳到第二步，只考虑技能 / 本地脚本 / 内联。
- **是** → 过下面六条 MCP 硬门槛，命中任一 → 必须做成 MCP（同时通常还需要技能来规定方法）。

#### MCP 六条硬门槛

| # | 门槛 | 一句话判断 | 命中即 MCP |
| --- | --- | --- | --- |
| 1 | **凭证不可见** | 凭证能让 Agent 看到吗？（含沙箱、环境变量） | 不能 → MCP，凭证只在服务端 |
| 2 | **有状态 / 常驻连接** | 需要会话、token 刷新、长连接、订阅推送吗？ | 需要 → MCP |
| 3 | **执行位置受限** | 目标系统只有特定网络或机器能访问吗？ | 是 → MCP 部署在可达位置 |
| 4 | **必须硬拦截** | 护栏能只靠"建议"吗？（写操作、生产环境） | 不能 → MCP 层做权限、审批、审计 |
| 5 | **多客户端复用** | 多个 Agent / 客户端要接入同一能力吗？ | 是 → MCP 标准协议 |
| 6 | **机器级契约** | 调用需要类型校验、结构化输入输出吗？ | 是 → MCP tool schema |

### 第二步：再过技能六条硬门槛（命中任一 → 必须做成技能）

| # | 门槛 | 一句话判断 | 命中即技能 |
| --- | --- | --- | --- |
| 1 | **不可逆 / 对外写** | 做错了能回退吗？ | 不能 → 技能（写确认门） |
| 2 | **凭证 / 敏感** | 会碰客户或生产密码吗？ | 会 → 技能管安全边界（只写"怎么用"，不写"是什么"） |
| 3 | **隐性方法** | 换个 Agent 会做错或漏做吗？ | 会 → 技能 |
| 4 | **确定性逻辑** | 每次重写会不一致吗？ | 会 → 技能 + 技能内脚本 |
| 5 | **团队一致性** | 多人多 Agent 要同一行为吗？ | 要 → 技能 |
| 6 | **可发现性** | 不写下来就没人知道存在吗？ | 是 → 技能 |

### 第三步：全不命中，再看频率与复用

```
MCP门槛 + 技能门槛
   |
   |- 命中MCP任一 ———— MCP(能力/硬护栏)+ 技能(方法/软护栏)
   |- 仅命中技能任一 ——— 技能(+ 技能内脚本)
   |- 全不命中
         |
         |- 高频、团队复用 ———— 本地共享库/脚本
         |
         |- 一次性、低频 ———— 对话内联,直接让AI做
```

#### 缺口重叠与优先级

第七节的完整例子把两套门槛几乎全中，看着干净，却把"只中一两条 + 偶发"的真实情况藏住了。补三条取数原则：

- **硬缺口优先于软缺口**：命中「连通性 / 强制性 / 凭证不可见」这类 MCP 硬门槛时，没有逃生舱——能不能安全连、能不能被强制拦，是前提，必须 MCP，与频率无关。
- **只中技能门槛、不碰外部系统**：技能独立成立，按频率决定做成技能还是本地库，无需 MCP。
- **命中凭证但偶发**：不要无脑起常驻 MCP，先过"成本维度"——见第七节的"反例"。

还有一个被原文档带过来的表面矛盾：第三步说"全不中 → 低频内联"，但技能门槛 3 又说"隐性方法缺了换个 Agent 就做错"。化解办法是——一次性任务若方法已被某个已有技能 / 知识库覆盖，则内联时直接调用该技能即可，不必新建；只有当方法本身不存在且不可逆风险低时，才允许纯对话内联。

两条补充规则，专门用来消除"到底放哪"的模糊地带：

- **技能内脚本 vs 共享库**：脚本只服务于某一个技能的确定性步骤，放在技能目录内；被多个技能或多个团队复用、且不含业务口径的通用能力，下沉为共享库。
- **本地脚本 vs MCP**：无状态、无凭证、沙箱内可跑的纯计算（解析、OCR、格式转换）用本地脚本；一旦涉及凭证、会话、内网，就不要再用本地脚本硬扛。

### 第四步：凭证永远单独处理

无论是否做成技能或 MCP，**凭证都不进对话、不进技能正文、不作为 tool 参数传入**，统一由密钥管理注入到 MCP 服务端或 gitignored 配置。技能里只写"怎么用凭证"，不写"凭证是什么"；Agent 只传业务参数。

## 四、分工：脑与手的双层护栏

```
MCP   = 手:能做什么(连接、权限、执行、审计),强制
技能  = 脑:何时做、按什么顺序、哪些要确认,指引
类比  = MCP 是 Agent SDK 的能力包,技能是它的使用说明书
```

典型组合是两者一起用：MCP 提供工具并按读 / 写拆分，技能规定流程、状态机和"写操作前必须让人确认"。

**不可逆操作采用双层护栏**——这是整篇最该记住的一张表：

| 层 | 机制 | 性质 | 作用 |
| --- | --- | --- | --- |
| 技能 | 写确认门、流程状态机 | 软 | 让 Agent 知道该停下来问人 |
| MCP | 写 tool 单独拆出，设审批 / 权限 / 审计 | 硬 | 即使 Agent 漏读、误读或被注入，也越不过去 |

> 技能本质是写给 Agent 的指引，可能被漏读、误读或绕过；真正不可逆的操作，必须在工具层有硬拦截。

这就是为什么"只在技能里写一句请先确认"是危险的——它是"软"的，依赖 Agent 读到了、读懂了、且没被注入要求绕过它。生产环境的写操作，硬拦截必须落在 MCP。

## 五、分层落地：各归各位

把东西放进对的层，比写得多详细更重要：

| 层 | 放什么 | 判断标准 |
| --- | --- | --- |
| **知识库** | 客观事实 / 方法论 | 跨版本稳定、可检索 |
| **技能** | 方法 / 契约 / 护栏（软，Agent SDK 的说明书） | 换人做会做错、漏、越界 |
| **MCP** | 有凭证 / 有状态 / 跨网络的能力 + 硬护栏（Agent SDK 的能力包） | 命中 MCP 六条门槛 |
| **本地库 / 脚本** | 无状态、无凭证的确定性计算 | 沙箱内可跑、多次复用 |
| **对话内联** | 一次性 / 动态操作 | 低频、可逆、结果容忍差异 |
| **密钥管理** | 凭证 / 密码 | 只在 MCP 服务端或配置中，不进对话、不进技能 |

**分层原则**：知识归知识、方法归技能、连接与强制归 MCP、纯计算归本地库、凭证归密钥、一次性归对话。任何东西放错层，都会产生重复、漂移或泄露。

## 六、反模式清单（精选）

这些反模式在实际项目里极其常见，挑几个最容易踩的：

| 反模式 | 症状 | 正确做法 |
| --- | --- | --- |
| **把通用能力做成技能** | 连接、看图、HTTP 各一个技能，同类实现重复 | 无凭证的下沉为本地库；有凭证 / 内网的做成 MCP |
| **把密码放对话** | 密码进对话记录、shell 历史、上下文 | 密钥管理 / gitignored 配置，由 MCP 服务端持有 |
| **把知识塞进技能** | 技能正文堆事实清单，版本一变就错 | 事实进知识库，技能只留方法 |
| **只靠技能做安全护栏** | 不可逆操作只有"请先确认"的文字提示 | 技能写确认门 + MCP 做硬拦截，双层护栏 |
| **把 MCP 当普通 SDK 直接搬** | 凭证塞进 tool 参数、方法写进 tool description、暴露万能 tool | 按 Agent SDK 重新封装：能力面进 MCP（凭证 / 连接藏服务端），用法面进技能 |
| **一个 API 一个 tool** | tool 泛滥，描述撑爆上下文 | 按任务意图聚合，少而精 |
| **万能 tool** | 暴露 `execute_sql`、`run_shell`，指望技能约束 | 读写拆分、白名单化、最小权限 |
| **凭证作为 tool 参数传入** | 密码又回到对话里 | 服务端持有，Agent 只传业务参数 |

## 七、一个具体例子：连内网数据库跑对账

光有表不够，走一遍最直观。假设需求是："连内网数据库，用生产凭证做对账，并把差异结果写回。"

**先过 MCP 六条硬门槛：**

- 门槛 1 凭证不可见：生产凭证不能让 Agent 看到 → **命中**。
- 门槛 2 有状态 / 常驻连接：数据库连接 + 凭证刷新 → **命中**。
- 门槛 3 执行位置受限：数据库在内网，Agent 沙箱到不了 → **命中**。
- 门槛 4 必须硬拦截：写回是写操作、且是生产环境 → **命中**。
- 门槛 5 多客户端复用：多个 Agent / 报表系统都要查同一库 → 视情况命中。
- 结论：**必须做成 MCP**，而且读 tool 和写 tool 要分开，写 tool 挂审批 / 权限。

**再过技能六条硬门槛：**

- 门槛 1 不可逆 / 对外写：写回差异结果，做错难回退 → **命中**。
- 门槛 2 凭证 / 敏感：碰生产凭证 → **命中**（技能只写"用凭证连接"，不写密码）。
- 门槛 3 隐性方法：对账的步骤、顺序、对账口径，换个 Agent 会做错 → **命中**。
- 门槛 4 确定性逻辑：分页、去重、对账计算，每次重写会不一致 → **命中**（放进技能内脚本）。
- 结论：**必须做成技能**，规定流程、状态机和"写回前必须让人确认"。

**第四步：凭证单独处理** —— 生产凭证只登记在密钥管理，由 MCP 服务端注入，Agent 只传"要查哪张表、对哪两个字段"。

最终形态：**MCP（连接 + 读 / 写拆分的工具 + 硬护栏）+ 技能（对账方法 + 确认门）+ 凭证只在服务端**。三者各司其职，没有把密码塞进技能，也没有只靠一句"请确认"兜底。

换成 SDK 的说法：我们为 Agent 封装了一个"内网对账 SDK"——凭证、连接、读写权限都藏在服务端，Agent 拿到的是几个带 schema 的 tool；而"对账方法 + 写回前确认"就是这个 SDK 的使用说明书（技能）。

### 反例：只命中凭证门槛、一年只用两次

上面的例子是教科书级"全中"，回避了最棘手的情况。来一个"脏"的：

**场景**：偶尔需要连一次内网数据库查一个数，一年大概两次，平时根本用不上。

**过门槛**：MCP 门槛里只命中「凭证不可见」（1）和「执行位置受限」（3，内网）；但它是无状态的单次查询，不命中"有状态 / 常驻"、"多客户端复用"、"机器级契约"；技能门槛几乎不中（不是不可逆写、没有复杂确定性逻辑，换成谁都会做）。

**矛盾点**：按原决策树"命中 MCP 任一 → 必须做成 MCP"，结论是要为一年两次的调用起一个常驻 MCP 服务。这显然不划算——起服务、维连接、做权限、留审计，维护成本远超两次使用的收益。

**逃生舱（成本维度）**：决策不能只看"是否命中"，还要看**频率 × 维护成本**。对这个场景更合理的做法是：

- **人工代理连接**：由人在旁路用已授权的凭证连内网、执行查询，Agent 只负责拼查询语句和解读结果；
- **临时凭证 + 对话内联**：通过密钥管理临时签发短时效凭证，Agent 在一次性对话里跑完即焚，不起常驻服务；
- **只有当"使用频率 / 复用客户端数"跨过某条线**时，才值得把它沉淀成常驻 MCP。

一句话：**命中硬缺口解决的是"必须能做"，但是否"值得做成常驻服务"，还得让频率和维护成本说话。** 这正是前几节没说透的地方，也是本文最该补的一刀。

## 八、速览清单：一张表带走

新建技能或 MCP 前，按这个清单过一遍：

- [ ] 先判断是否碰外部系统 / 凭证 / 状态；是则逐条过 **MCP 六条硬门槛**，记下命中哪条。
- [ ] 再逐条过 **技能六条硬门槛**，记下命中哪条。
- [ ] 两边全不命中 → 不进技能 / MCP，按频率走本地共享库或对话内联。
- [ ] 命中硬缺口（连通性 / 强制性 / 凭证）→ 必须 MCP，与频率无关；命中凭证但偶发 → 先过成本维度再决定。
- [ ] 凭证单独登记到密钥管理，不写进技能正文、不作为 tool 参数。
- [ ] 不可逆操作必须有**双层护栏**：技能里有确认门，MCP 里写 tool 已单独拆出并有审批或权限。
- [ ] 用 SDK 类比自检：MCP 承担"能力面"（凭证 / 连接 / 权限藏在服务端），技能承担"用法面"（顺序 / 状态机 / 确认门）；不要把凭证塞进 tool 参数、不要把方法写进 tool description。

评审时再补四眼：是否重复了已有能力（尤其连接、HTTP、OCR）；知识是否放错层；不可逆操作是否双层护栏；MCP 的 tool 是否按意图聚合、读写是否拆分、是否暴露了万能 tool。

定期复核用**缺口类型**而不是"AI 现在能不能"——被模型覆盖的"一致性 / 接入型"技能、被平台原生能力替代的自建 MCP，都要做降级评估。

## 九、写在最后

这套方法论的骨架其实只有一句话：**不要问"AI 会不会"，要问"它缺哪类东西"。**

当你下次又想争论"这个到底要不要做成技能 / MCP"时，把问题从"AI 能力够不够"换成"它缺的是信息、权限、方法、确定性、责任、连通性、强制性里的哪一类"——答案往往会自己浮出来，而且不会因为下一个更强模型发布就作废。

落到记忆点：

- **MCP = Agent 用的自定义 SDK = 手（硬）**：能力面——能连到哪、能做什么、谁在强制；凭证与连接藏在服务端。
- **技能 = 这份 SDK 的使用说明书 = 脑（软）**：怎么做才对、何时停、按什么顺序。
- **凭证 = 谁都不进**：不进对话、不进技能、不作为 tool 参数，只在服务端。
- **不可逆 = 双层护栏**：技能确认门 + MCP 硬拦截，缺一不可。
- **硬缺口优先、成本兜底**：连通性 / 强制性 / 凭证这类硬门槛无逃生舱，必须 MCP；但"命中凭证却偶发"要先算频率与维护成本，别为一年两次的调用硬起常驻服务。

> **本文没展开的两块（留给落地工程）**：① MCP 服务端本身的信任边界——"凭证只在服务端持有"默认你信任该服务端，租户隔离、审计留痕、服务端加固需另行设计；② Skill 与 MCP 之间的契约回归与版本兼容——按 SDK 类比，就是 tool schema 一变，如何不破坏依赖它的技能（说明书），需要独立的兼容性管理。这两块属于"做成之后怎么守住"的工程细节，不在"要不要做"的判定范围里。
